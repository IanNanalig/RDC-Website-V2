# Suggested Manual Beta-Testing Workflow

1. Create test accounts through the normal account/role workflow; do not use database tools.
2. Create Projects 01, 03, 04, 06, and 10 from their primary-agency Contributor accounts and upload the relevant PDF listed in each project file.
3. For Projects 04 and 05, select `DOTr` as the collaborating agency while retaining `DPWH` as the primary agency. Confirm only the DPWH contributor can edit. Project 04 is designed to be submitted so DOTr can test view-only collaboration access.
4. Create Projects 02, 05, and 07 without a document. Save drafts, then attempt submission and record the required-document result. Do not claim those drafts were submitted until a suitable document is actually added.
5. Create Projects 08 and 09 and upload only their specified unrelated PDF. Submit them only if the normal form permits it, then have a Validator test whether document assessment identifies the mismatch.
6. A Validator should review submitted projects using the live review interface. Enter only evidence-based validator facts required for AI preflight; do not edit contributor-owned answers.
7. Run AI priority analysis only where the configured provider and required facts are available. Record any provider or document-assessment limitation honestly. Do not create a final priority confirmation or endorsement unless the tester completes that actual workflow.
8. Test a return-for-update path on one submitted project, then verify only fields selected by the Validator can be changed by the primary contributor.
9. Verify public transparency/dashboard visibility only after a project is genuinely endorsed through the live workflow. The kit does not pre-create public, validated, or confirmed records.
