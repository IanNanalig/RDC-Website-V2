Agency root cause: `Projects.tsx` builds options from `project.agency` plus both `collaborating_agencies[].name` and `.code`, then filters with exact text equality. `PublicProjectSerializer.get_agency` prefers the saved form's text and does not expose the existing `primary_agency` foreign key. Therefore DSWD and its full name can appear as separate options and a selected text value need not match every project from the same agency. The public list and stats APIs also filter agency by text, with no canonical-ID parameter. The fix will derive public agency identities from relationships first and resolve unique legacy code/name matches without changing stored answers.

Implementation: the public serializer now supplies `primary_agency` and collaborator ID/code/name, preferring the primary-agency relationship and otherwise resolving saved text only when a catalog code or name matches uniquely after case and whitespace normalization. Unknown legacy text is retained as a distinct visible option; no agency or project record is rewritten. The list and statistics APIs accept `agency_id` and resolve recognized legacy `agency` text through the same identity. The public cache schema was bumped. The dashboard uses one option per agency ID and filters both primary and collaborating projects by that ID. The Status dropdown omits Not Implemented, but its records and API filter remain available. The Municipality dropdown omits Unspecified, while unfiltered projects with `lgus=[]` remain visible and counted. Unknown location text is not assigned a city; production records need a separate authorized data review to identify specific cleanup candidates.

## Project update and regrading regression investigation (2026-11-10)

Baseline: the previous local `projects cms` run passed 430 tests, with 2 skipped. This investigation has not changed hosted data. A disposable local PostgreSQL service was not found on PATH; PostgreSQL-specific concurrency verification remains a separate gate.

Confirmed causes in the current source:

1. `ProjectRevisionSerializer` exposes `workflow_status`, but the Validator project list converts revisions into frontend rows without copying that property. Its badge can therefore fall back to the internal `state="submitted"`, which is a valid revision state but not a project workflow status.
2. The Validator revision queue includes `state="reviewed"`, the state used when an update was returned for correction. That keeps a returned submission in the active queue. The Reviewed & Endorsed screen fetches only base projects, so completed progress revisions have no matching history row.
3. Contributor `start-update` calls `prepare_project_migration(..., trigger="contributor_update")` when the saved form is old, despite the Administrator migration workflow. An Administrator-prepared draft pins the new form version while the base project intentionally retains the validated old version, which requires every list to select the active draft marker consistently.
4. The current AI endpoints are project-scoped and read `project.profile_data` and `active_project_documents(project)`. Pending revision data and evidence are absent from those inputs; analyses have no revision association. Validator evaluation and confirmation also require the base project to be Pending Validation, which is false for a validated project with a pending update.

Implementation order: make submission status and queue lists authoritative; enforce Administrator form preparation and same version selection across roles; add revision-scoped analysis/evidence/confirmation and approval gate; audit ambiguous stored records; run API and browser regressions. Preserve the latest endorsed public snapshot and all historical scores.

## Scope and baseline

Reviewed the Contributor progress-update form, `ProjectRevision` routes, Validator revision queue, supporting-document API, and the separate correction/resubmission route. All reproduction and tests used Django's isolated local SQLite test database. No hosted records were changed. The existing uncommitted priority-analysis changes and sample kits were left in place.

## Reproduction and root causes

1. The backend `start-update` route creates a progress revision. The revision update and submit routes persist it and the Validator queue includes submitted revisions. A local API regression confirms **Start Update → submit → queue** works.
2. The frontend progress-revision branch returned immediately after saving/submitting. It skipped the queued-file upload step used by ordinary submissions. The same form disabled document changes in revision mode. Consequently, selected update evidence was never attached, even though the update could be reported as submitted.
3. Documents had only a project relationship. A new document for a pending revision therefore could not be distinguished from the validated project's effective evidence. The document list also fetched assessment status jointly with files; for a Validator opening a submitted progress revision on an ongoing project, that assessment request could be forbidden and hide the otherwise accessible file list.
4. The separate initial correction path already permits document changes only when the Validator selects that document field. It continues to use the original project submission route and is not merged with progress updates.

## Changes

- Added an optional document-to-revision relationship and a migration. Current project evidence includes original project documents and documents from endorsed revisions. Pending and rejected revision documents remain linked to their revisions but do not enter effective evidence or AI assessment inputs.
- Allowed Contributors from the primary agency to attach or remove documents on editable progress revisions, subject to the progress window, field access, file validation, count, size, and checksum rules. Validators can read documents on submitted revisions. Existing project documents remain read-only during an update.
- Preserved Validator document access after endorsement by recognizing the project's persisted revision history. A completed update no longer drops the reviewer's ability to download its supporting document.
- Changed the progress form to upload files against its revision before submitting it. A failed upload leaves the revision in draft and shows a failure message; success feedback appears only after the submit request succeeds. Document loading no longer depends on the separate AI assessment request.
- Scoped the active checksum uniqueness rules so rejected revision evidence does not prevent an identical upload in a later revision. Existing effective-document duplicate checks remain.
- Kept revision state changes as the switch that makes endorsed evidence current; no file bytes or historical project answers are rewritten at endorsement.
